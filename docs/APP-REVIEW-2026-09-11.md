# LAN Share App · 全面评价报告

> 评价对象：Flutter 移动端 App（`mobile/`，v0.28.2+76，86 个 Dart 文件 / 24,918 行）
> 评价日期：2026-09-11　评价依据：**静态统计 + 测试基线 + 历史审查报告 + 本次实测**
> 方法说明：本报告全部结论均可复现（统计命令与数据来源见 §八）。**未做**真机压力测试、
> 弱网实测与长时间挂机观测，涉及这三项的判断已在下文明确标注为"未验证"。

## 一、总体结论

**这是一款功能覆盖远超"个人练手项目"的家庭网盘 App，短板不在能做什么，而在代码怎么长、以及改完之后靠什么保证没改坏。**

一句话概括五个维度的落差：**产品能力是 4.5 分的水准，而工程护栏只有 3 分的强度**——项目把资源几乎全部投给了服务端与 Web（`项目记忆/11` 显示服务端的耦合、流程、生产等价性已从 2–1 分修到 5 分并落成 CI 守卫），App 侧 2026-09-10 审查点名的结构债**原样保留至今**。

| 维度 | 评分 | 一句话依据 |
|------|------|-----------|
| 功能完整性 | ★★★★☆ **4.5** | 浏览/传输/自动备份/分享/笔记/管理面全线可用；缺 iOS 认真适配、离线缓存、i18n |
| 界面与交互设计 | ★★★★☆ **4.0** | 六色板 + M3 + AMOLED 视觉系统成熟，本次补上响应式；但无障碍 0 处、页面内视觉字面量仍有 ~199 处 |
| 性能与稳定性 | ★★★★☆ **4.5** | Sliver 虚拟化 / 四层图片缓存 / 弱网并发分账 / 断点续传都是真功夫；但无性能基线测试守护 |
| 代码质量 | ★★★☆☆ **3.0** | 注释与文档优秀、零 TODO、静态分析全绿；但**分层失效 51 处、7 个千行文件、11 份重复 toast** |
| 用户体验 | ★★★☆☆ **3.5** | 交互细节讲究（长按多选/拖动排序/空态引导）；但读屏完全不可用、无离线模式、错误反馈粒度粗 |
| **综合** | **★★★★☆ 3.9 / 5** | 产品优等生，App 侧工程债待偿 |

## 二、功能完整性 ★★★★☆

### 2.1 做到了什么（超出预期的部分）

App 不是"网页套壳"，而是有真正独立价值的原生端：

| 能力 | 说明 |
|------|------|
| **相册自动备份** | WorkManager 周期任务 + MediaStore Observer 防抖 + 前台 dataSync 服务；后台 isolate 拉起独立 FlutterEngine 跑纯 Dart 引擎；账本 `(id, mtime, size)` diff 去重 + `session_id` 断点；**250MB 杀进程零重传实测通过** |
| **智能对账** | 轮前三步：空间预检 → 改名识别（≥5 张同向迁移 + 旧相册消失则服务端 rename 不重传）→ 相册被删识别，账本加 `server_missing` 状态机 |
| **离线优先的传输引擎** | 队列 JSON 落盘（800ms debounce + 5s 强制刷盘）、断点真值在服务端、登录态联动自动续传/挂起 |
| **系统级集成** | 系统分享接收、生物识别 + 应用锁、配对码免密登录、内置 TOTP 验证器（RFC 6238 自实现零依赖）、检查更新 + 更新历史 |
| **管理面** | 成员/邀请/授权/通知运营/会话治理全在 App 内可用（与 Web 控制台对齐） |
| **文档预览矩阵** | 图/文/MD/Word/HEIC/docx/xlsx/csv/pptx/rtf + "用其他应用打开"兜底 |

功能完整度这一项，**放在个人/家庭项目里属于顶格水平**。

### 2.2 缺口

1. **iOS 只是"能装"**：`pubspec.yaml` 里 `flutter_native_splash` 显式 `ios: false`，说明 iOS 开屏、图标、后台策略都没有认真做过。`APP-DESIGN §9` 把 iOS 后台限制列为"平台硬限制、不做全量承诺"——这是**合理的取舍**，但意味着 iOS 用户拿到的是一个半成品体验。
2. **无离线模式**：`项目记忆/10` 把"离线缓存"列为未做项。现在断网只能看错误页（虽然有针对性的断网横幅），不能浏览已缓存的元数据。
3. **无 i18n**：`pubspec.yaml` 未引入 `flutter_localizations`，全 App 中文硬编码。家庭场景可接受，但**代码里所有文案都是字面量**，将来要国际化等于全文重写。
4. **笔记能力有功能重叠风险**：知识库/图谱在 v0.26.0 被整体下线，但 `notes_page.dart` 仍有 1,573 行（全仓最大文件），承载分类体系 + 三个编辑器 + 拖拽 + 批量移动——**功能下线没有带来代码瘦身**。

## 三、界面与交互设计 ★★★★☆

### 3.1 优点：视觉系统是真的成体系

这不是"随手调了个色"的项目：

- **主题引擎**：6 套预置色板（种子色 + 品牌渐变 + 深色底）+ Material You 跟随壁纸；暗色**不用 M3 中性灰**，而是从色板深底向上派生表面阶梯（`_tier`），任意色板下都和谐；AMOLED 纯黑独立一档
- **品牌语言统一**：云朵 + 渐变底贯穿登录页/品牌头/空态/二维码/启动图标，`make-app-icon.py` 单一生成源
- **视觉基调克制**：卡片 `elevation: 0` + 0.6px 描边分界，只有真正的浮层才用阴影——避免了家庭类 App 常见的"卡片堆阴影"廉价感
- **本次补上的两块**：设计令牌层（间距 4pt 网格 / 圆角 / 动效 / 图标 / 阴影 / 描边）与响应式断点（600 / 840，清单页限宽 720，网格列数自适应），并配 14 项回归测试

### 3.2 问题

1. **无障碍完全缺失——0 处 `Semantics` / `semanticLabel`**（全仓静态统计）。这意味着 TalkBack 用户打开 App 只能听到一堆无意义的图标与拼读的英文路径。**家庭网盘的用户里有老人，这是真实的可用性损失，不是纸面指标。**
2. **视觉令牌"立了规矩，迁移才刚开始"**：页面层仍有 **约 199 处 `EdgeInsets` 字面量**（notes_page 22 / backup_settings_page 25 / home_page 17 / photos_page 15 / me_page 14 …）。本次只完成了基础设施与 7 个页面的适配，**40 个页面里大部分还没迁**。
3. **平板体验刚起步**：本次才补上"限宽 + 增列"，真正的**双栏布局**还没做。平板上目前是"变宽的手机界面"，而不是利用大屏的信息架构。
4. **横屏未验证**：品牌头高度固定 78（与屏高无关，理论上安全），但**没有任何页面做过横屏实测**，属于"看起来没问题"。

## 四、性能与稳定性 ★★★★☆

### 4.1 扎实的地方

- **列表虚拟化彻底**：照片墙从"ListView + shrinkWrap 网格"改造成 `CustomScrollView` + Sliver（0.4.4 真机复现"划走再回来全变转圈"后重构），并因上游 `flutter_staggered_grid_view` 在同一滚动视图多个瀑布流下的致命 bug（issue #265/#286/#338）换成 `waterfall_flow`
- **图片链路四层缓存**：`AuthImage` 鉴权 + 磁盘缓存 + 失败回退类型图标；缩略图服务端 PIL/ffmpeg 生成
- **弱网分账是动过脑子的**：局域网 8 路缩略图并发 / 公网 3 路；大图预览 1280 → 960；照片墙每页 120 → 60；上传并发 2 → 1；超时与重试策略按入口区分
- **稳定性细节**：`database is locked` 类问题的 commit 规则、`_db_lock` RLock 嵌套、后台 isolate 与主 isolate 的 prefs 隔离——这些都是踩过坑才有的设计

### 4.2 隐患

1. **性能没有基线测试守护**：`项目记忆/03` 记着"改了照片墙/图片链路必须加跑快滑压力测试"，但这是**人工纪律**，不是自动化。全套 166 项测试里没有一个性能或内存用例。
2. **`shrinkWrap: true` 仍散落 9 处**（多数在底部弹层等小列表，属合理用法；但这类写法在 Flutter 里是典型的性能反模式，缺少一条 lint 或约定来防止它被误用到长列表）。
3. **单文件过大的间接代价**：`backup_settings_page.dart` 1,523 行里挂着一个 **2s 周期 Timer**（`:45`），且 State 里跑着完整业务流（清空服务端备份的两步确认、口令复核 HTTP、在途轮次拦截、异常恢复调度）。这类"Widget 里跑业务"会让性能问题的定位成本成倍上升。
4. **未验证项**：72h 挂机稳定性、弱网真机压测、平板/横屏实测——都没有做。

## 五、代码质量 ★★★☆☆

### 5.1 值得肯定的部分

- **注释是稀缺的高质量**：几乎每个文件头部都有"为什么这样做 + 哪一版踩了什么坑 + 现在怎么解"，例如 `home_shell.dart` 记录应用锁"恶性锁死"的三环根因、`app_theme.dart` 记录墨水方向写反导致"全 App 白字画浅卡"。**这种注释密度在同规模项目里极罕见。**
- **零 `TODO` / `FIXME` / `HACK`**（全仓静态统计）——技术债没有以注释形式腐烂，而是被记进文档里
- **静态分析全绿**：`dart analyze lib` → No issues found
- **契约与错误层有单点**：`data/api/api_client.dart`（Dio + Bearer + 401 统一 + 重试拦截器）、`errors.dart`（统一错误文案）、`data/media_kinds.dart`（扩展名事实源）

### 5.2 问题（这是本次评价最重的部分）

**问题 1：分层设计存在但被系统性绕过 —— UI 层 51 处直发请求**

静态统计 `mobile/lib/ui/**` 中 `ApiClient.I.dio()` 直接出现 **51 次**，分布 14 个文件：

| 文件 | 处数 | 文件 | 处数 |
|------|-----|------|-----|
| `admin_page.dart` | 12 | `photos_page.dart` | 7 |
| `album_detail_page.dart` | 7 | `files_page.dart` | 6 |
| `notifications_page.dart` | 6 | `trash_page.dart` | 4 |
| `recent_page.dart` | 2 | 其余 7 个文件 | 各 1 |

**为什么这是问题**：`data/api/` 里已经建好了 `files_api` / `notes_api` / `account_api` / `feedback_api` / `home_api` 五个模块（v3.43~v3.49 收编了 26 处），证明**分层是可行的、也已有先例**——只是没有强制，于是新代码继续绕过。后果是后端契约一变更，要在 14 个 UI 文件里找散落的 URL 拼接与 JSON 取值（`项目记忆/03` 记着"契约缺陷是跨端共债"的教训）。

**问题 2：7 个千行文件，最重的两处是"一个文件装多个页面 + 业务逻辑"**

| 文件 | 行数 | 问题 |
|------|------|------|
| `notes_page.dart` | 1,573 | 两个页面类同文件，仓储逻辑（`_load` 手写逐字段 JSON 映射、CRUD + 对话框）全在 State |
| `backup_settings_page.dart` | 1,523 | **一个文件 4 个页面类**（BackupSettingsPage / BackupDetailsPage / BackupBucketsPage / ServerAlbumsPage），State 跑完整业务流 |
| `files_page.dart` | 1,346 | 4 个文件类型 + 双布局 + 多选 + 移动/复制/重命名/分享/详情 |
| `me_page.dart` | 1,197 | 身份 + 设备 + 5 个设置分组 + 3 个对话框 |
| `admin_page.dart` | 1,138 | 三页签管理面 |
| `home_page.dart` | 1,111 | 7 种卡片 + 拖动排序 + 各自轮询 |
| `photos_page.dart` | 1,048 | 时间线 + 筛选 + 月份快跳 + 多选 |

`ui/` 目录 18,699 行占全 App 的 **75%**，而 `data/` 只有 2,943 行（12%）。**UI 层过重、数据层过薄**，与 `项目记忆/07` 的 P1 判断完全一致。

**问题 3：UI 层几乎没有自动化回归保护**

这是最容易被忽视、但后果最直接的一条：

| 指标 | 实测值 |
|------|--------|
| `flutter test` 总数 | 166 项全绿 |
| 其中 `testWidgets`（能测 UI 的） | **13 处** |
| 扣掉本次新增的 `visual_tokens_test.dart`（8 处） | **原有 152 项里仅 5 处** |
| golden 测试 | **0** |

**含义**：这 166 项测试覆盖的是 TOTP 算法、上传协议数学、文档提取、令牌阶梯——**全是纯逻辑**。任何一次改主题、改布局、改交互，**都没有测试会告诉你改坏了什么**。本次改主题之所以能相对安心，靠的是"手机竖屏观感不变"的设计约束 + 人工判断，而不是测试保护。

这也解释了为什么项目要花大量精力写"踩坑清单"与"验收方法论"——**因为测试护栏的缺口是用人的记忆在补**。

**问题 4：重复实现仍在**

`void _toast(String msg)` 在 UI 层重复定义 **11 次**（`album_detail_page` 一个文件里就有 2 份，因为有两个页面类）。`项目记忆/07` 早已建议收编到 `ui/widgets/kit.dart`，至今未做。

## 六、用户体验 ★★★☆☆

### 6.1 优点：细节是想过的

- **长按多选 + 拖动排序 + 管理卡片显隐**（首页卡片可自定，本机 prefs）
- **空态三件套**（云朵 + 标题 + 引导按钮）替代"还没 xx"灰字
- **断网横幅只认"连不上"**：4xx/5xx 不伪装成断网（服务端可达与网络不可达是两件事）
- **危险操作二次确认**（退出登录是全 App 唯一无确认的高危操作，已补确认框）
- **应用锁有逃生口**：指纹解不开可用密码重登，且做了"弹窗自身的生命周期不算切后台"的判定（0.6.0 恶性锁死三环修复）
- **传输完成系统通知**、上传进度、秒传跳过——长任务有反馈

### 6.2 问题

1. **读屏用户完全不可用**（同 §3.2-1）——这是 UX 维度最严重的一条
2. **错误反馈粒度粗**：虽然有 `errors.dart` 统一文案，但大量场景止步于 SnackBar 一句话，缺少"为什么失败 + 怎么办"（例如上传失败是配额、权限还是网络）
3. **无离线模式**：地铁里打开 App 只能看到错误页
4. **首次引导缺失**：家庭里非技术用户第一次打开，需要自己搞清"服务器地址从哪来"（虽有扫码/配对码兜底，但无引导流程）
5. **字号缩放未验证**：遵循系统 `textScaleFactor`，但**没有用大字号实测过**任何页面，字放大后是否溢出未知

## 七、主要优点（Top 5）

1. **产品能力顶格**：自动备份的"账本 + 智能对账 + 后台 isolate"组合，是很多商业网盘 App 都不具备的完整度
2. **注释与文档是真正的资产**：12 份项目记忆 + 每文件"为什么"注释 + 踩坑清单，换人接手成本极低
3. **弱网/离线工程扎实**：断点续传真值在服务端、队列落盘防"饿死"、按入口分账并发——这些是最难补、最晚才做对的东西，项目早期就做对了
4. **视觉系统成体系**：色板/暗色派生/AMOLED/品牌组件库/令牌/响应式，是"设计过的"而非"凑出来的"
5. **安全与权限设计有真正的单点**（服务端 `spaces.resolve()` / `filetools.safe_path()`，"能寻址≡有权限"），App 端证书 TOFU 信任也处理得当

## 九、改进建议（按投入产出排序）

### 批次 A · 低垂果实（每个都小、收益明确）

1. **拆 `backup_settings_page.dart` 成 4 个文件**——4 个页面类本就无共享状态，边界现成，是纯搬移（`项目记忆/07` 已给出方案）
2. **建 `ui/widgets/kit.dart` 收编 `_toast`**（11 处）与 `confirmDialog` 等重复件
3. **加 3–5 个 golden 测试**守关键页面的视觉快照（首页卡片流 / 我的页 / 照片墙空态）——这是补 UI 护栏**最便宜**的起点
4. **加一条 lint/守卫**禁止 `ui/` 目录 import `dio`（后端已有 AST 守卫先例，照抄即可）

### 批次 B · 分层收口

5. **按域继续收编 51 处裸 dio**：`admin_api` / `album_api` / `trash_api` / `notifications_api` 四个模块就能吃掉 29 处（12+7+4+6）。已有五个模块的先例，路径清晰。
6. **拆 `notes_page.dart`**：仓储逻辑抽 `notes_repository.dart`，两个页面类分文件。

### 批次 C · 体验补课

7. **无障碍关键路径补齐**：登录页、首页卡片、文件列表、底部导航先加 `Semantics` 标签——不必全量，覆盖主干流程即可显著改善

10. **平板双栏**——建议先看真机反馈再定

### 明确不建议现在做的

- **不要为了"结构好看"重写页面**：24,918 行的 App 且 UI 层零测试护栏，大重构的风险远大于收益
- **不要先做 i18n**：家庭场景中文单语没有痛点，且当前文案全是字面量，成本极高
- **不要在补齐 UI 测试前做视觉大改**：本次令牌化已经把"改视觉"的成本降下来了，先补护栏再动手更稳
