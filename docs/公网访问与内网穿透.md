# 公网访问：把网盘暴露到你家之外

> 面向主人自己的操作手册。以**樱花 FRP** 为主，末尾附其它穿透工具的差异点。
> 托盘面板「公网访问 → 怎么配置？」里是同一份流程的精简版。

---

## 0. 先搞清楚一件事：填地址≠能用

很多人第一反应是「穿透工具给了个地址，粘进面板就行」。**不行。**

本机的 HTTPS 证书是 Caddy 用内部 CA 签的，**只对配置里写明的名字有效**：

```
localhost / 127.0.0.1 / 本机局域网 IP
```

穿透工具给你的 `cn-bj.frp.one` 不在这个名单里。客户端拿它去连，会在
**TLS 握手阶段被直接掐断**（实测报错 `SEC_E_INTERNAL_ERROR`，HTTP 状态码
`000`）—— 连 HTTP 层的错误页都出不来。

所以链路是三步，顺序不能反：

```
① 穿透工具建隧道（把公网流量送到本机 8765）
② 本机认这个域名（写进 Caddy 配置 + 重签证书）   ← 面板的「一键接入」干这个
③ 面板里填完整公网地址（一键接入成功后自动填好）
```

---

## 0. 地址必须带 `https://`（2026-11-06 实机）

浏览器里输入 `你的域名:端口`，会对非标准端口补 `http://`，然后撞上樱花的
**明文 HTTP 合规拦截**：

```
501 Not Implemented  #20
您正试图使用 HTTP 协议访问此隧道
因为下面的原因，此请求已被拦截：
  · 执行机房的内容合规要求和有关部门的管控规定
Powered by Sakura Frp
```

这个页面是**樱花服务器回的，请求根本没到你的电脑**。验证方法：

```bash
curl  -s -o /dev/null -w '%{http_code}' "http://你的域名:端口/up"    # → 501
curl -sk -o /dev/null -w '%{http_code}' "https://你的域名:端口/up"   # → 200
```

正确写法：**`https://你的域名:端口`**，包括 `https://`。首次打开会弹自签证书
警告，点「高级 → 继续前往」。

## 1. 建错了会怎样（2026-11-04 实机记录）

这是最容易踩的坑，先看症状再动手，能省一轮排查：

| 你看到的 | 说明 | 怎么办 |
|---|---|---|
| 托盘「一键接入」成功，从公网访问却 **TLS 握手失败 / 打不开** | 隧道建成了 **HTTPS 或 HTTP 类型** | 改成 **TCP 类型** |
| 公网 `http://域名:端口` 返回 **501 Not Implemented**，`Server: SakuraFrp` | 同上：穿透服务端在替你做 TLS，但它拿不到你的自签证书 | 改成 TCP 类型 |
| 托盘「验证」提示「穿透服务端直接应答了」 | 同上 | 改成 TCP 类型 |

**原因**：本机是 Caddy 用自签证书提供的 HTTPS。TCP 类型隧道把 TLS 字节流
原样送到本机，握手由 Caddy 完成，一切正常。而 HTTPS/HTTP 类型隧道由**穿透
服务端**接管 TLS —— 它需要你在服务商面板上传证书，而我们的证书是本地自签的，
既传不上去、外部客户端也不会信。

4.0.3 起「一键接入」会真的从公网地址连一次，失败时直接告诉你是不是这个原因；
之前的版本只在本机验证域名，会误报成功。

## 1. 穿透侧：建一条 TCP 隧道

以樱花 FRP 为例：

1. 打开 <https://www.natfrp.com>，注册并登录
2. 下载客户端（Windows 版），用账号的**访问密钥**登录
3. 「隧道」→ 新建隧道：

   | 字段 | 填什么 | 说明 |
   |---|---|---|
   | 隧道类型 | **TCP** | 不要选 HTTP；本机是 HTTPS，HTTP 隧道会二次反代出问题 |
   | 本地地址 | `127.0.0.1` | 必须回环，不是 `0.0.0.0` |
   | 本地端口 | `8765` | 本机 Web 端口（安装时可能改过，以面板显示为准）。填 `8767` 也通 —— 那是历史文档里的隧道端口，Caddy 同样监听 |
   | 远程端口 | 挑一个没被占的，如 `35123` | 免费用户通常要在它给的区间里选 |
   | 绑定域名 | 默认给它给的节点域名 | 一般不用改 |

4. 启动隧道，确认状态是「在线」
5. 记下完整地址：**节点域名 + 远程端口**

   ```
   cn-bj.frp.one:35123
   ```

> 樱花有多个节点，域名各不相同（`cn-bj.frp.one` / `cn-hk.frp.one` …）。
> 换节点 = 换域名 = 要重新接入一次（见第 3 节）。

## 2. 本机侧：让 Caddy 认这个域名

### 推荐：面板一键接入

托盘面板 →「公网访问」→ 把 `cn-bj.frp.one:35123` 粘进**隧道域名**输入框 →
点 **「一键接入」**。

程序会依次做：

1. 解析出域名 `cn-bj.frp.one`
2. 把它追加进 `conf\Caddyfile` 的站点地址行（保留原有的 localhost / 局域网 IP）
3. 备份原配置到 `Caddyfile.wanbak`
4. 重启 Caddy 服务 → 内部 CA 为新域名签证书
5. 从**公网地址**真连一次 `/up`（不是只在本机测域名）

   早期版本只在本机用 SNI=域名探 `/healthz`，那只证明「本机 Caddy 认这个域名」，
   和外面能不能访问是两回事，会误报成功。现在探的是公网 `域名:端口`。
   探针用 `/up` 而不是 `/healthz`：后者在公网入口被有意收敛成 404（磁盘水位不外泄）。
6. 通过后把 `https://cn-bj.frp.one:35123` **自动填进公网地址并保存**

失败时会把失败的那一步和原因直接显示出来（比如 TLS 握手失败 = 域名没被认）。

### 手工方式（不推荐，仅备用）

改 `conf\Caddyfile` 的站点地址行，把域名加进去（**保留 `:8765`**）：

```caddyfile
https://localhost:8765, https://127.0.0.1:8765, https://192.168.1.100:8765, https://cn-bj.frp.one:8765 {
	tls internal
	...
}
```

然后重启服务：

```powershell
Restart-Service lanshare-caddy
```

⚠ 这个文件头部写着「不要手改」——重装/升级会重新生成，手改内容会丢。
一键接入是同一套逻辑，但会保留原有主机名，且能被重复执行。

## 3. 验证

1. **手机切到移动流量**（关键：不要连家里 WiFi，否则走的是局域网路径，
   验不出公网）
2. 打开 `https://cn-bj.frp.one:35123`
3. 浏览器提示「证书不受信任」→ 点「继续访问」（自签证书，正常现象）
4. 看到网盘登录页 = 通了

手机 App 里：服务器地址填同一个 URL，首次连接会弹「信任此服务器」（显示
SHA256 指纹），点信任即可，之后不再问。

## 4. 排错表

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 浏览器「无法连接」/ 超时 | 隧道没在线，或本地端口填错 | 回樱花客户端看隧道状态 |
| 樱花日志刷「连接映射目标 tcp://127.0.0.1:xxxxx 失败，连接被拒绝」 | 隧道里的本地端口在本机没人听 | 改成 8765 或 8767（Caddy 只开这两个） |
| `ERR_SSL_PROTOCOL_ERROR` / 握手失败 | **域名没接入本机**（最常见） | 先点「一键接入」 |
| 打开是 404 | 域名进了 Caddyfile 但站点块没匹配 | 检查站点地址行有没有该域名 |
| 能打开但提示证书错误 | 自签证书，正常 | 点继续；App 里点信任 |
| 局域网能开，外网不行 | 隧道不通 | 看樱花客户端日志 |
| 之前能用，换节点后不行 | 域名变了 | 用新地址重新「一键接入」 |

## 5. 其它穿透工具

流程完全一样，只是第 1 步的界面不同。要点：

- **必须用 TCP 隧道**，本地目标 `127.0.0.1:8765`（或 `8767`）
- 拿到「域名:端口」后，一样粘进「隧道地址」点一键接入
- frp 自建：`[web] type=tcp, local_ip=127.0.0.1, local_port=8765, remote_port=xxxx`，
  域名取 `subdomain.你的域名` 或直接用服务器 IP（IP 也能接，同样的道理）

> 用 frp 自建且**域名走你自己的公网 CA**（不是 Caddy 内部 CA）时，可以跳过
> 一键接入直接填地址 —— 那种情况下证书本来就是公网可信的。但只要证书是
> 本机 Caddy 签的，就必须先接入。

---

## 6. 两个长期注意事项

**IP 会变**：`Caddyfile` 里的局域网 IP 是安装/开启局域网时写进去的。路由器
换了网段（比如 `192.168.1.x` → `192.168.0.x`），局域网那份配置就失效了 ——
重新点一次「开启局域网服务」即可。公网域名不受影响。

**证书到期**：本机根 CA 有效期 10 年（到 2036）。到期那天所有设备会同时报
证书错误，面板会提前一年提醒。

## 7. 方式二：自有域名（Cloudflare Tunnel）

前六节讲的是**穿透服务商给你地址**。如果你有**自己的域名**并托管在
Cloudflare，还有一条更省事的路：Cloudflare Tunnel。

### 7.1 为什么这条路和 FRP 不一样

FRP 那条必须「一键接入」，因为**本机证书是 Caddy 自签的**，Caddy 只对配置里
写明的域名签证书，陌生域名一来就在 TLS 握手阶段被掐断。

Cloudflare Tunnel 完全不同：

```
浏览器 ──HTTPS(443)──> Cloudflare 边缘 ──隧道──> 本机 8766
                       ↑ 证书在这里终止
                         用的是 Let's Encrypt 公共证书
```

**TLS 在 Cloudflare 边缘就终止了**，到你本机是隧道内部的一跳。所以：

- 不用改 Caddyfile
- 不用重签证书
- 客户端（手机 App、浏览器）**看到的是正规公共证书，零配置**

这也是为什么它比 FRP 省事：**你只需要告诉程序「我的公网域名是这个」**。

### 7.2 前置条件

- 有一个域名，且**NS 已经托管在 Cloudflare**（免费的就行）
- 本机能装 `cloudflared`

### 7.3 建隧道（在你自己机器上）

```bash
# 1. 下载 cloudflared（Windows 版，免安装）
#    https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe

# 2. 登录（会跳浏览器，选你的域名点授权）
cloudflared tunnel login

# 3. 建隧道
cloudflared tunnel create lanshare
#    → 记下输出的 ID，类似 8fb79f64-5192-4bdd-adfe-b4c4541f7639

# 4. 把域名指到隧道（会自动创建 CNAME 记录）
cloudflared tunnel route dns lanshare lanshareapi.你的域名.com
```

### 7.4 写配置并装成服务

新建 `cloudflared.yml`：

```yaml
tunnel: <第 3 步的隧道 ID>
credentials-file: C:/Users/<你>/.cloudflared/<隧道ID>.json
protocol: http2          # QUIC 在部分家宽上被限速，http2 通常更快

ingress:
  - hostname: lanshareapi.你的域名.com
    service: http://127.0.0.1:8766
    originRequest:
      httpHostHeader: lanshareapi.你的域名.com
  - service: http_status:404
```

> **为什么指向 8766 而不是 8765（Caddy）**：Caddy 的站点是按 Host 精确匹配的，
> 新域名要改生成器才能认。而 Caddy 那层主要做「静态资源直发 + `/updates/*`」，
> 静态资源 API 自己也能发（实测 `/assets/*.js` 直连 8766 是 200）。
> 代价是 `/updates/*` 不可用（见 7.7）。

装成服务（开机自启、崩溃自动拉起）：

```bash
nssm install LANShareTunnel "C:\lanshare\bin\cloudflared.exe" ^
    --config "C:\lanshare\conf\cloudflared.yml" --loglevel info tunnel run lanshare
nssm set LANShareTunnel Start SERVICE_AUTO_START
nssm start LANShareTunnel
```

### 7.5 托盘里启用

托盘面板 →「公网访问」→ **方式二：Cloudflare Tunnel** → 填
`https://lanshareapi.你的域名.com` → 点「检测并启用」。

程序会跑四步检测，**任何一步失败都不会保存**：

| 步骤 | 检查什么 | 失败时说明 |
|---|---|---|
| 格式 | https、无端口、无路径、不是 IP、不是 CF 自有域名 | 「不要填端口，Cloudflare 固定 443」 |
| 解析 | 域名解析到哪（仅诊断，不阻塞） | 「域名没走 Cloudflare 代理，把橙色云朵打开」 |
| 连通 | 从本机请求公网地址 | 按 CF 错误码给具体建议（见 7.6） |
| **同源** | 比对公网与本机的 `/api/instance-id` | **「这个域名指向的不是这台机器」** |

> **同源校验为什么必须有**：如果只验「HTTPS 能通」，用户少打一个字母、域名指向
> 了别人的 LANShare，验证照样通过 —— 然后 App 就连到别人家去了。

检测结果下面还有两项**环境提示**（只提示、不阻止启用）：
本机有没有装 cloudflared、cloudflared 进程在不在跑、TUN 模式有没有开着。

> **TUN 模式是唯一会「必然失败」的环境因素**：Clash 的 TUN 会把所有 DNS 查询
> 劫持成 `198.18.x.x` 假地址，cloudflared 连不到真边缘。看到红字提示就先关 TUN。

### 7.6 排错表

| 你看到的 | 真实原因 | 怎么办 |
|---|---|---|
| `Cloudflare 1033` | 隧道建好了但没连上 | 检查 cloudflared 是否在跑，点「启动隧道」 |
| `Cloudflare 1034` | CNAME 目标不对 | 确认指向 `<隧道ID>.cfargotunnel.com` |
| `Cloudflare 1010` | 请求被指纹拦截 | 不影响 App（Dio 的 UA 不会被拦），检测本身可忽略 |
| `Cloudflare 1016` | 域名不在你的账号 | 确认域名 NS 托管在这个账号 |
| `Cloudflare 526` | 边缘到源站证书问题 | SSL/TLS 模式改成 Full 或 Flexible |
| `Cloudflare 502/503` | 隧道通了但本机没响应 | 检查 LANShare 主服务是否在跑 |
| 「解析到 x.x.x.x（不是 Cloudflare）」 | 橙云没开 | 打开 DNS 记录的橙色云朵 |
| 「实例标识不一致」 | 域名指向了**别人**的 LANShare | 检查 DNS 指向哪条隧道，或域名拼错了 |
| 「连接超时」 | 隧道没建 / TUN 干扰 | 先关 TUN，再确认隧道在线 |

### 7.7 三条已知限制

**① `/updates/*` 在本机这个入口下不可用**

因为 ingress 直连 8766（API），绕过了 Caddy。更新包请走
`dl.ak47zzq.com`（R2）或你配置的其它更新源。

**② Cloudflare 免费版单请求上限 100MB**

LANShare 的分片上限是 64MB，所以**走分片的大文件没问题**。
但如果有单次请求超过 100MB 的路径，会被 Cloudflare 挡成 413。

**③ 国内访问走海外边缘，上行可能很慢**

实测（成都家宽）：下行 3.26 MB/s 正常，**上行只有 0.1–0.3 MB/s**，
CF-RAY 落点是 `LAX`（洛杉矶）。表现是：登录、看文件列表、看元数据都正常，
但传/拉大文件会很慢，5MB 分片就可能超过 Cloudflare 的 100 秒超时被判 524。

局域网内使用完全不受影响（不走隧道）。

### 7.8 「停用」和「停止隧道」不是一回事

| 操作 | 效果 |
|---|---|
| 「停用」/ 切换入口 | 只改**程序对外公布的地址**。隧道还在跑，那个域名仍然可以访问 |
| 「停止隧道」 | **真的停掉 cloudflared 服务**，公网立刻断。可以再「启动隧道」恢复 |

> ⚠️ 切换入口**不会关闭任何隧道**。以为「切到 Cloudflare 就等于关掉了 FRP」
> 是错的 —— frpc 还在跑，那条老地址照样能从公网进。
> 要真正关掉某条路，必须停掉对应的客户端程序。

**FRP 那条路程序管不到**：frpc 是你自己起的外部进程（樱花客户端叫
`SakuraFrpLauncher.exe`，原版叫 `frpc.exe`，Docker 里根本没有本机进程），
瞎猜着杀进程很可能误杀你**别的**隧道。所以 FRP 侧只给提示，不在界面里提供开关。
