# 更新源协议（自定义更新地址）

> 这份文件是**契约**。服务端 Python（`lanshare_cli/updater.py`）和手机端 Dart
> （`mobile/lib/data/update_service.dart`）都按它实现，改字段必须同步改两边和本文件。

## 为什么要自定义源

默认从 GitHub Releases 拉更新。GitHub 在国内不稳（限流、墙、代理），而且发一次
版就要等 Release 上传完。自己维护一个更新接口，可以把「改一行 JSON + 传个包」
当成发版，适合快速迭代。

## 设计取舍

选的是**单文件清单**，不是模仿 GitHub API：

- 你要维护的东西只有一个 `index.json` 和一个放包的目录，扔 Caddy / nginx 后面开
  静态托管就能用，**不需要写服务**
- 最新版和更新历史在同一个文件里，客户端一次请求全拿到
- 模仿 GitHub API 看着"兼容"，实际是给自己找了个新活：字段一多容易做错，
  GitHub 将来改字段你还得跟着改

## 地址怎么配

**支持多个地址，按填写顺序尝试，第一个能用的就用**。局域网地址写在前面，
公网（隧道）地址写在后面 —— 在家直接走内网，不绕一圈公网。

```
https://192.168.1.100:8765/updates      ← 局域网，优先
https://cn-bj.frp.one:35123/updates     ← 樱花隧道，其次
```

配置落点：

| 位置 | 存哪 | 谁读 |
|---|---|---|
| 服务端 | 注册表 `HKLM\SOFTWARE\LANShare` 的 `UpdateUrls`（多行，一行一个） | `lanshare_cli`、托盘 GUI |
| 手机端 | 本地设置（shared_preferences） | App |
| 手机端「跟随服务器」 | 服务端 `/api/app/latest` 返回的 `update_source` 字段 | App 默认用它 |

手机端不填 = 跟着服务器走；填了 = 直连你填的地址。

## 清单文件

地址栏填到目录或文件都行：

| 你填的 | 实际请求 |
|---|---|
| `https://host/updates` | `https://host/updates/index.json` |
| `https://host/updates/` | `https://host/updates/index.json` |
| `https://host/updates/index.json` | 原样 |

### `index.json`

```json
{
  "schema": 1,
  "latest": {
    "version": "3.96",
    "build": 396,
    "url": "https://192.168.1.100:8765/updates/LANShare-Setup-3.96.exe",
    "sha256": "f31e1963364e28940bc51a40a094ee67f37d276b01a8b82c232befbb7b1e8a45",
    "size": 56890036,
    "notes": "本次更新说明，可以多行",
    "published": "2026-11-04"
  },
  "history": [
    {
      "version": "3.95",
      "build": 395,
      "published": "2026-11-03",
      "notes": "一句话摘要"
    },
    {
      "version": "3.94",
      "build": 394,
      "published": "2026-11-03",
      "notes": "公网访问一键接入"
    }
  ]
}
```

### 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | 是 | 目前只认 `1`。将来改结构时靠它分流 |
| `latest.version` | 是 | 形如 `3.96` / `3.96.1`。跟安装目录 `VERSION` 文件比 |
| `latest.build` | 否 | 整数，手机端优先用它比（APK 的 versionCode 更可靠） |
| `latest.url` | 是 | 安装包直链。**相对路径也接受**：按清单**所在目录**解析（填目录或 `.../index.json` 文件形式都一样——文件形式剥掉文件名取目录）；相对地址且无基准目录时按缺 `url` 作废。服务端 `updater.py::_abs_url` 与 App 端 `update_source.dart::resolveUrl` 必须同步改 |
| `latest.sha256` | 是 | 64 位十六进制。下载后校验，不匹配**拒装** |
| `latest.size` | 否 | 字节数。用于显示进度和提前校验 |
| `latest.notes` | 否 | 更新说明，Markdown |
| `latest.published` | 否 | `YYYY-MM-DD` |
| `history[]` | 否 | 同上结构但只需 `version` / `published` / `notes` |

### 硬性规则

清单缺 `version`、`url`、`sha256` 任何一项 → **整份清单作废**，当作这个源不可用。
不猜、不降级容错：更新链路上"宽容"等于给用户装一个来路不明的 exe。

## 回退链

```
① 自定义源（按配置顺序，逐个试）
        ↓ 全挂 / 没配
② GitHub Releases（server-v* / app-v*）
        ↓ 也挂
③ 上次成功结果的本地缓存（标注"来自 N 小时前"）
        ↓ 什么都没有
④ 明确报错
```

**回退必须标注来源**。自定义源连不上却静默回落 GitHub，用户会以为"源里没有新版"，
实际是源挂了 —— 这比报错更难查。所以结果里永远带：

```json
{
  "source": "custom",              // custom | github | cache
  "source_url": "https://192.168.1.100:8765/updates",
  "source_error": ""               // 自定义源失败的原因（回落时填）
}
```

UI 上必须显示成「自定义源连不上（TLS 失败），以下结果来自 GitHub」这种带原因的话。

## 安全

- **只接受 `https://`**。填 `http://` 直接拒绝并说明原因（明文分发可执行文件，
  中间人改一下就是远程代码执行）。唯一例外：`127.0.0.1` / `localhost` 允许 http，
  给自己调试用。
- **`sha256` 强制校验**，下载完对不上拒装。
- 不做清单签名。信任边界是你的服务器；签名防的是"服务器被黑"，属于下一阶段。

## 发版流程（用自定义源时）

1. 打安装包 / APK，算出 sha256
2. 传到更新目录（例：`updates/LANShare-Setup-3.96.exe`）
3. 改 `index.json`：把旧 `latest` 塞进 `history` 头部，写新的 `latest`
4. 完事。客户端下次检查更新就能看到

> 手动改 JSON 容易漏字段。维护脚本建议放 `tools/publish_update.py`（待建），
> 负责算 sha256、挪 latest 进 history、校验必填项。
