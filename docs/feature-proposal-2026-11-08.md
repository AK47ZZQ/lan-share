## 1. 项目根本目标与用户价值（第一性原理）

这是一个 2–20 人家庭自包含网盘（FastAPI + PG16 + Vue3 + Flutter），主人与家人的
照片、分享、授权是**真实生产数据**。从第一性原理看，产品的根本存在条件不是功能多寡，而是：

1. **数据不灭**（存在性）：全家的记忆唯一存于此机。照片原图单拷贝 = 唯一的存在性风险
   （路线图明文）。机器整机常关机、无第二块物理盘（本机仅 C:）。
2. **数据可取**（可用性）：LAN/公网对等可达，认证在应用层；App 自动再发现保证家人
   手机在网络切换后自动回到正确入口。
3. **数据只给该看的人**（授权面）：`spaces.resolve()/visible()` 收口一切文件入口。
4. **坏了能发现**（可观测）：健康日报、loop_health、审计环、巡检、反馈看板。

主人 2026-10-24 冻结令（主人指令，记录于路线图）：**照片第二份拷贝完成首次真实备份前
不排期新功能批**；修复、运维、安全批不受限。解冻条件 = `scripts/backup_files_external.py`
完成首次真实运行。因此本夜的「功能发现」空间被治理规则收窄为：**把解冻条件本身推进，
或做修复/运维/安全批**。这不是我保守，是仓库治理的最高优先指令。

## 3. 候选功能清单与证伪

### 候选 A（选定）：外部备份链路「插盘即跑」保障批（运维+修复）

**根本问题**：解冻条件是一个从未运行过的脚本；等主人真插盘时第一次跑就撞上它自己的闸。
**证据（当夜运行时实证）**：
- **缺陷①（盘符根闸 off-by-one）**：`_validate_dest` 用 `len(parts) <= 2` 判盘符根，
  把合法的两层目标（`E:\lan-share-files`，parts=2）一起拒掉。实测：`C:\lansbak-a-probe`
  → "拒绝写入盘符根"。
- **缺陷②（dry-run 谎报）**：dry-run 清点的是**目标侧**（空）→ 永远报 "0 文件 / 0 GB"，
  主人将无法用 dry-run 评估备份规模。纸面审查定位，WB3 演练实证。
- **缺口③（对账单侧）**：manifest 只记目标侧清点数，无源侧对照 → 对账无从谈起
  （robocopy rc<8 只保证"没失败"，不保证"拷全了"）。
- **缺口④（无持久证据）**：robocopy 只有 /TEE（控制台），无 /LOG —— 无人值守跑完
  无 per-file 证据可查。
- **证伪尝试（对抗式）**：
  - "不做也行？"——不做则解冻条件永远悬置，主人插盘首跑即失败（缺陷①），
    或拿到 0 文件的假报告（缺陷②）。判：必须做。
  - "有更简单方案？"——曾设想"预跑一次真实备份到 C: 同盘副本"直接解除冻结，
    **被否决**：主人明确"第二块盘/异地备份搁浅"，同盘副本不构成主人语义下的
    第二份拷贝（存在性风险针对整机/整盘损失），且 19G 同盘复制与生产 I/O 争抢。
    也不做 GUI/托盘/定时触发（主人 09-13 暂停过计划任务备份，定时触发需拍板）。
  - "违反 YAGNI？增加耦合？"——脚本零新依赖、零 schema 变更、零服务代码改动；
    修复限于脚本自身 + 单测。最小垂直切片。
- **消融计划**：改坏盘符根闸（`< 2`→`<= 2` 或直接删闸）→ 新用例必须红；
  删掉 dry-run 源侧清点 → 用例红。消融产物留档。
- **验收标准**：
  1. `--dest C:\name`（两层合法目标）不再被拒；`--dest C:\`（真盘符根）仍拒。
  2. dry-run 报源侧预计规模（非 0）。
  3. manifest 含源/目标侧清点 + `match` 布尔 + robocopy 日志路径（v3.70 已有 robocopy_rc）。
  4. 隔离重演：合成树增量×2、清单对账 match=true、二次运行 rc=0 且清点不变；
     生产规模只读 dry-run（零写入）给出真实预计规模。
  插盘首跑成功率从"未验证"提升到"演练过"。

### 候选 B（次选，做）：release.py 本地暂存目录清理（运维，P3 挂账）

**根本问题**：`C:\lanshare\updates\` 每版 57MB 累积（现 4 版 ≈228MB + app/ 子目录）。
**证伪**："不做也行？"——盘 64%，近期无紧迫性；但这是明文挂账项，且修复成本一小时级。
**对抗审查发现（比挂账原文更进一步）**：`updates\` 现由托盘更新器使用（index.json +
多版本安装器供一键更新与 4.0.13 的回滚看护）。**盲目"清旧"可能砍掉回滚能力**——
挂账原文写于 4.0.13 回滚看护落地之前，结论已过时。故正确做法不是"清"，是
**flag-gated 保守清理**：只删 `LANShare-Setup-*.exe` 中版本号严格小于"保留窗"
（默认最新 N=2 个）的安装器；`index.json(.bak)` 与 `app/` 一律不碰；默认不跑，
`--prune-updates-dir` 显式开启；无人值守批**只交付能力不自主运行**（生产布局，
留主人拍板）。挂账原文的"~471MB/3 版"数字与现盘面不符（4 版≈228MB），以实测为准。
**消融**：把"保留窗"改坏成删全部 → 用例红。
**风险**：回收站重定向使"删除"可能不真释放——但 installers 可由 build.ps1 重建，
风险可接受；本批不自主运行，跑与不跑留主人。
