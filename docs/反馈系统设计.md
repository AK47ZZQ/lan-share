# LAN Share 反馈系统 · 架构与设计

> 状态：设计定稿（2026-11-06）
> 覆盖：App / 网页 / 托盘 三端入口；单机自用与分发给他人两种形态

---

## 1. 目标

**一句话**：任何装了 LAN Share 的人，在任何一端（手机 / 浏览器 / 托盘）都能提交反馈；
反馈先落在提交者本地（断网不丢），再自动汇到开发端；开发端能收到提醒、看板管理、回写处理状态。

**不是**工单系统，**不是**客服聊天，**不做**用户注册。范围就这么大。

### 三种部署形态

| 形态 | 谁在用 | 反馈怎么走 |
|---|---|---|
| **单机自用** | 你自己 | 提交 → 本地库 → 你自己看（relay 可关） |
| **分发给他人** | 别人装你的包 | 提交 → 他的本地库 → relay → **你的接收端** |
| **开发端** | 你（接收多方） | 收件箱 + 看板 + 通知 + 状态回写 |

同一份服务端代码要同时扮演这三种角色 —— **靠配置区分，不靠分支代码**。

## 2. 总体架构

```
┌────────────────────── 提交者的机器 ──────────────────────┐
│                                                          │
│  App(Flutter)   网页(Vue)   托盘面板(WebView2)            │
│       └────────────┼────────────┘                        │
│              POST /api/feedback  (需登录)                 │
│                    ▼                                     │
│         ┌──────────────────────┐                         │
│         │ 本地 LAN Share 服务端 │                         │
│         └──────────────────────┘                         │
│            │            │                                │
│            │            └──► SSE: kind=feedback          │
│            │                 （通知管理员的铃铛）          │
│            ▼                                             │
│   data/反馈/待处理/<fid>.md  +  img/<fid>-N.ext          │
│            │                                             │
│            │ 反馈看板.md（regen）                         │
│            ▼                                             │
│        relay（异步，失败只记日志）                          │
└────────────┼─────────────────────────────────────────────┘
             │ HTTPS  POST /api/feedback/inbox
             │ Authorization: Bearer <token>
             ▼
┌────────────────── 开发端（你的机器）──────────────────────┐
│                                                          │
│   POST /api/feedback/inbox                               │
│     ├─ token 恒定时间比较（未配置 → 403，绝不 fail-open）  │
│     ├─ 来源白名单（防 ../ 穿越）                          │
│     ├─ 每来源每日条数上限（防刷爆磁盘）                     │
│     ├─ 字段截断（防当存储桶用）                            │
│     └─ fid 幂等（重发不重复写）                            │
│                    ▼                                     │
│   data/反馈/收件箱/<来源>/<fid>.md                        │
│                    │                                     │
│        ┌───────────┼───────────┐                         │
│        ▼           ▼           ▼                         │
│   看板.md      邮件/飞书     网页「反馈管理」              │
│               通知          （改状态 → 回写）             │
└──────────────────────────────────────────────────────────┘
```

### 为什么是「先本地、再 relay」，而不是客户端直连接收端

| 维度 | 先本地再 relay（选定） | 客户端直连 |
|---|---|---|
| 断网 | 本地已落盘，恢复后补传 | 直接丢 |
| 提交者配置 | 装好即用（分发时预置） | 他要填你的地址和 token |
| token 暴露面 | 只在服务端配置里 | 每个客户端都存一份 |
| 本地服务挂了 | 提不了（用托盘入口兜） | 能提 |

最后一条的代价用**托盘入口**兜住：网盘服务起不来时，托盘还活着，它走 IPC 直接把反馈写文件，不依赖 API。

## 3. 数据模型

### 3.1 单条反馈的落盘格式

`data/反馈/待处理/<fid>.md`（UTF-8，LF）：

```markdown
---
编号: 20261106145254-678d
类型: bug                    # idea | bug | question | other
状态: 已提交                  # 已提交 | 已查看 | 处理中 | 已完成 | 不处理
备注:                        # 开发端回写的一句话
标题: 局域网开关点了没反应
版本: 4.0.8+135
设备: Android · BP2A.250605.031.A3
用户: user@example.com       # 单机形态下是本人；跨机上报时**不携带**
来源: zzq-pc                 # 跨机时标识哪台机器，取自该机的 feedback_source
创建: 2026-11-06 14:52:54
更新: 2026-11-06 15:10:02
---

正文内容，可多段。
```

附件：`data/反馈/img/<fid>-1.jpg`、`-2.png`（白名单：jpg/jpeg/png/gif/webp/txt/md）

### 3.2 目录布局

```
data/反馈/
├── 待处理/<fid>.md              ← 新提交、未关闭
├── 已完成/<fid>.md              ← 状态=已完成|不处理
├── img/<fid>-N.ext              ← 附件（两处共用）
├── 收件箱/<来源>/<fid>.md        ← 跨机上报进来的（开发端独有）
├── 看板.md                      ← 自动生成，人机共读
└── .bak-已完成/                  ← 历史归档
```

> **为什么用 Markdown 而不是数据库里的表**：
> 反馈是低频、长文本、带附件的**人类文档**，不是高并发事务数据。落成文件的好处是
> 直接能用编辑器改、能 git 管、坏一个不影响其他、以及——最重要的一点——
> **agent 可以直接读写它**（本项目大量维护工作由 agent 完成）。

### 3.3 状态机

```
已提交 ──► 已查看 ──► 处理中 ──► 已完成
   │                      │
   └──────────────────────┴──► 不处理
```

- 只有开发端（接收端）能改状态
- 改状态后通过 `append` 回写，提交者下次打开详情能看到
- 「不处理」必须带 `备注`（为什么不做），否则等于静默丢弃

## 4. 接口设计

### 4.1 已有接口（本次沿用，不重写）

| 方法 | 路径 | 鉴权 | 用途 |
|---|---|---|---|
| POST | `/api/feedback` | 登录用户 | 提交（multipart，含附件） |
| GET | `/api/feedback` | 登录用户 | 我的反馈列表 |
| GET | `/api/feedback/{fid}` | 登录用户 | 详情 |
| POST | `/api/feedback/{fid}/append` | 登录用户 | 追加内容/回写状态 |
| GET | `/api/feedback/{fid}/img/{name}` | 登录用户 | 附件 |
| GET | `/api/admin/feedback` | admin | 全部反馈（开发端用） |
| POST | `/api/feedback/inbox` | **Bearer token** | 跨机上报入口 |
| GET | `/api/feedback/inbox/status` | admin | 收件箱状态 |

### 4.2 需要新增

```http
POST /api/feedback/{fid}/status
Content-Type: application/json
{ "status": "处理中", "note": "已定位，是 Caddy 重写配置时丢了域名" }

→ { "ok": true, "status": "处理中" }
> admin only。状态变更必须写审计日志。
```

```http
GET /api/feedback/inbox/sources
→ { "sources": [{ "name": "zzq-pc", "count": 12, "last": "2026-11-06 15:02" }] }
> admin only。看有哪些机器上报过、各多少条。
```

```http
POST /api/feedback/open          ← 免登录兜底入口（登录页用）
Content-Type: application/json
{ "title": "...", "body": "...", "type": "bug", "app_ver": "...", "hp": "" }

→ { "ok": true, "id": "2026..." }
> 不落盘到「待处理」，而是落 收件箱/open/<fid>.md，
> 且强制带来源标记 open，与登录用户的反馈分开管理。
> 限流：每 IP 每日 3 条；hp 字段是隐藏的蜜罐，填了直接丢弃。
```

### 4.3 relay 侧配置（settings 表）

| 键 | 含义 | 默认 |
|---|---|---|
| `feedback_relay_enabled` | `1` 才上报 | `0`（**默认关**） |
| `feedback_relay_url` | 接收端地址，如 `https://your-frp.example.com:48429` | 空 |
| `feedback_relay_token` | 与接收端 `feedback_inbox_token` 相同 | 空 |
| `feedback_source` | 本机标识，出现在收件箱目录名里 | `lanshare` |
| `feedback_inbox_token` | 接收端校验用 | 空 = 收件箱不开门 |

**安全约定**：token 用 `hmac.compare_digest` 做恒定时间比较；未配置时**返回 403 而不是放行**（fail-closed）。

## 5. 三端入口

### 5.1 网页端（新增页面 `web/src/views/FeedbackView.vue`）

```
侧边栏 ── 反馈
├── 列表：我的反馈（标题 / 类型 / 状态 / 时间）
│     └─ 状态用颜色区分：已提交(灰) 已查看(蓝) 处理中(橙) 已完成(绿) 不处理(灰虚线)
├── 新建：标题 / 类型 / 正文 / 拖入截图（≤3 张，每张 ≤25MB）
└── 详情：正文 + 附件缩略图 + 状态时间线 + 「补充说明」
```

字段和 App 的 `feedback_page.dart` **完全对齐**，只是渲染层不同。

### 5.2 App 端（已有，补两处）

- 详情页显示**状态**和开发端回写的 `备注`
- 设置页显示「反馈上报：已开启 / 已关闭（点击切换）」

### 5.3 托盘面板（新增，走 IPC）

```
面板底部 ── 提反馈
└─ 弹一个精简表单：标题 + 正文 + 「附带最近的日志尾巴」
    └─ 走 WebPanel 的 Send/PostMessage 桥 → C# 侧直接写文件
```

**为什么托盘这条必须做**：网盘服务起不来的时候，网页打不开、App 连不上，**偏偏这时最需要提反馈**。
托盘是唯一还活着的进程，它写文件不经过 API。

### 5.4 登录页兜底（新增）

登录框下方一行小字：`登不上？点这里反馈（不需要登录）`
→ 走 `/api/feedback/open`，独立限流。

## 6. 隐私与告知（分发前的前置条件）

分发包里预置了 relay 目标，**等于默认把反馈发给开发端**。这必须做到：

| 要求 | 实现位置 |
|---|---|
| **首次启动告知** | 安装器完成页 + 首次登录后的弹窗，明确写：反馈会发送到 `<接收端域名>` 用于改进产品，可在设置里关闭 |
| **可关闭** | 设置 → 反馈上报 开关（写 `feedback_relay_enabled=0`），关掉后 relay 完全跳过 |
| **只发必要字段** | relay 的 payload 白名单：`id/title/type/body/app_ver/device/source/created`。<br>**不发**：文件附件、用户名、真实姓名、路径、IP |
| **用户能看见发了什么** | 反馈详情页显示「已上报 / 未上报（已关闭） / 上报失败（可重试）」 |
| **接收端能看到来源但看不到人** | `来源` 是设备别名（`zzq-pc`），不是邮箱；用户字段在跨机上报时置空 |

> 不做这几条，就是偷偷上报。装的人一旦发现会很不舒服，而且这个项目是要给别人用的。

## 7. 通知与看板

### 7.1 提交通知（提交者侧）

提交成功后，服务端发一个 SSE 事件：

```
event: feedback
data: {"kind":"feedback","fid":"2026...","title":"..."}
```

网页的 `NotificationsBell.vue` **已经**在处理 `kind === 'feedback'`，不需要改。

### 7.2 接收通知（开发端）

| 渠道 | 实现 | 状态 |
|---|---|---|
| 网页铃铛 | 上面的 SSE（admin 也收） | ✅ 已有 |
| 邮件 | Hermes 定时任务扫 `收件箱/`，发现新 fid 就发一封汇总邮件 | 待做 |
| 飞书 | 同上，走现有通道 | 待做 |

**为什么用定时扫描而不是在服务端里直接发信**：
服务端不该依赖邮件配置；扫描是幂等的（按 fid 去重），服务端重启也不会漏或重。

### 7.3 看板

`_regen_kanban()` 生成 `data/反馈/看板.md`：

```markdown
# 反馈看板（自动生成，勿手改）

## 待处理 3
| 编号 | 标题 | 类型 | 来源 | 创建 |

## 处理中 1
...

## 最近完成 5
...
```

人和 agent 读同一份文件 —— 这样我下次接手时，不用翻数据库就知道有哪些待办。

## 8. 安全边界

| 风险 | 防护 |
|---|---|
| 收件箱变成公网垃圾场 | 未配 token → 403；每来源每日上限；字段截断  |
| `../` 路径穿越 | `source` 和 `fid` 都过白名单正则 |
| 大附件打爆内存 | 分块读，超 25MB 立即中断并删半截文件（已有） |
| 免登录入口被刷 | 每 IP 每日 3 条 + 蜜罐字段 |
| token 泄露 | 恒定时间比较；只在服务端配置里，不进客户端 |
| 反馈里夹带敏感信息 | 提交页明确提示「不要贴密码/密钥」；附件不随 relay 上报 |
| 伪造来源刷屏 | `source` 由接收端按 token 归属记账，同一 token 下的来源名去重限流 |

## 9. 分发配置（给别人用的那一包）

安装器在写入服务端配置时，额外预置三个值：

```
feedback_relay_enabled = 1
feedback_relay_url     = https://your-frp.example.com:48429
feedback_relay_token   = <与你接收端一致的 token>
```

**接收端（你的机器）要做的**：

1. 配 `feedback_inbox_token` = 同一个值
2. 确保 `/api/feedback/inbox` 从公网可达（已经在 FRP 后面，路径 `/api/*` 本来就走 Caddy 反代）
3. 开邮件通知定时任务

**注意**：接收端地址必须是**提交者能访问到的**。如果你给的人在公司内网，而接收端只在自己家里 —— 那他的 relay 永远失败。
所以分发时要问一句：**你那边能访问 `<域名>` 吗**。不能就让他关掉 relay（本地照样能提，只是不汇总）。

## 10. 明确不做的事

| 不做 | 理由 |
|---|---|
| 用户账号体系 | 反馈不需要登录才能有价值；已有的登录用户直接复用，没登录的走 open 入口 |
| 工单流转/指派/优先级 | 你一个人处理，五个状态已经够 |
| 实时聊天 | 那是 IM 的活，飞书已经有了 |
| 反馈数据进 PG | 文件够用，而且 agent 更容易读 |
| 客户端直连 | 见 §2 的对比表 |
| 第三方表单服务 | 数据在自己手里，且不想多一个账号 |

## 12. 验收标准

- [ ] 手机上提一条反馈 → 5 分钟内收到邮件
- [ ] 网页端提反馈 → 列表里出现，状态是「已提交」
- [ ] 关掉网盘服务 → 托盘仍能提反馈，重启后能看到
- [ ] 另一台机器装上分发包 → 提反馈 → 出现在开发端的 `收件箱/<source>/`
- [ ] 把 `feedback_relay_enabled` 置 0 → 不再上报，本地仍有记录
- [ ] 收件箱收到 20MB 正文 → 被截断而不是写爆磁盘
- [ ] 用错 token 调 `/api/feedback/inbox` → 403
