# LAN Share 代码审查 + 对抗性安全审查 — Cron 任务 Prompt

> **⚠️ 纯只读任务：只分析、只报告，绝不修改任何代码文件。**
> 注册命令：在新 ZCode 会话中执行 CronCreate，prompt 内容从下方 `## Prompt` 开始复制。

## Cron 配置
- cron: `30 20 * * 1,4`（每周一/四 20:30）
- recurring: true
- title: `LAN Share 代码审查 + 对抗性安全审查`

## Prompt

LAN Share 代码审查 + 对抗性安全审查。工作目录 C:\lan-share。
**⚠️ 本任务是纯只读审查：只读代码、只分析、只写报告文件，绝不 Edit/Write 任何 .py/.ts/.vue/.dart 文件。**
以下是必须按顺序执行的完整流程，包含 5 轮审查 + 5 轮对抗性审查，不可跳过任何轮次。

## A. 变更检测（前置）

1. 执行 git log --oneline -10 获取最近提交
2. 执行 git diff HEAD~3 --name-only 获取最近 3 次改动的文件列表
3. 记录变更文件列表供后续轮次使用

## B. 五轮审查（每轮独立，逐轮递进）

### 第 1 轮：安全核心文件全量审查
目标：逐行审计安全基础设施，不留死角。

**必读文件（全量 Read）：**
- `app/spaces.py` — 路径解析安全核心
- `app/security.py` — 认证、会话、防爆破、审计
- `app/db.py` — 数据库层、SQL 安全、锁机制
- `app/config.py` — 安全相关配置常量

**审查要点：**
- spaces.py：resolve() 所有分支（裸路径/shared:/private:/incoming）、_own_private_rel() 二次拼接风险、normcase 折叠覆盖度、SHARE_ROOT 拼接点、admin 精确写入
- security.py：require_user Cookie→Bearer 链路、会话生命周期（create/renew/validate/revoke）、防爆破按账号+按入口分账、audit() 覆盖度、scrypt 参数
- db.py：所有 SQL 是否参数化、_db_lock 覆盖所有写操作、事务一致性、双引擎兼容
- config.py：TTL/限额常量是否合理

**输出格式：**
```

| 文件 | 行数 | 发现数 | 关键发现 |
|---|---|---|---|
| spaces.py | N | N | ... |

```

### 第 2 轮：业务逻辑模块审查
目标：审查所有 API 端点的业务逻辑正确性和安全性。

**必读文件（全量 Read）：**
- `app/api/files.py` — 文件操作最大攻击面
- `app/api/share.py` — 分享功能
- `app/api/webdav.py` — WebDAV 独立攻击面
- `app/api/admin.py` — 管理功能
- `app/api/auth.py` — 登录与设备 Token
- `app/api/notify.py` — 通知推送
- `app/api/system.py` — 系统端点

**审查要点：**
- files.py：上传 filename sanitization、分片原子写（_tmp_* + os.replace）、秒传 samestat 安全、移动/重命名冲突、删除/回收站、zip 下发敏感路径、Range 请求
- share.py：owner_id 隔离、票据去重并发、提取码暴力防护、定向分享 user_id 校验、分享过期
- webdav.py：_dav_auth 独立密码优先级、PROPFIND/GET/PUT/DELETE 权限、路径走 resolve()
- admin.py：改用户名原子性、重置密码全端登出、授权矩阵精确度、X-As-User 校验
- auth.py：登录 TOTP 分支、Token 签发/轮换/吊销、/api/auth/me Bearer 兼容
- notify.py：URL 模板注入风险、线程池有界、响应体无回注
- system.py：照片扫描节流、公开 URL 暴露面

**输出格式：**

## C. 五轮对抗性审查（每轮独立，逐轮递进）

**核心原则：站在攻击者视角，刻意寻找开发者不会主动想到的漏洞。每轮更换攻击策略和重点。**

### 对抗第 1 轮：路径穿越与注入攻击
**策略：穷举所有路径操作入口，构造恶意路径。**

逐一测试以下攻击向量（读代码验证，不是运行测试）：
- `../../.meta.db` → 能否读取数据库
- `%2e%2e/.meta.db`（URL 编码）→ 解码后是否被拦截
- `shared:private/../../other-user/` → 能否越权
- `private/../../shared/` → 能否从 private 逃逸
- `private\..\..\shared\`（反斜杠）→ Windows 路径穿越
- `private/legitimate\x00.jpg`（空字节）→ 截断攻击
- 文件名含 `../` → upload 是否 sanitize
- 文件名含 `:*?"<>|` → Windows 非法字符是否清理
- SQL 字符串拼接点 → 是否全部参数化

**输出：** 每个向量一行：`向量 → 代码位置 → 是否可利用 → 理由`

### 对抗第 2 轮：认证绕过与权限提升攻击
**策略：在每个认证检查点尝试绕过。**

逐一测试：
- 不带 Cookie 也不带 Bearer 访问 /api/files → 应 401
- 伪造 Cookie 值（随机字符串）→ 应 401
- 过期 Token 访问 → 应 401（检查 TTL 计算）
- 吊销后 Token 访问 → 应 401（检查 revoke 逻辑）
- TOTP 启用后只传密码不传 code → 应返回 totp_required
- member 调用 /api/admin/* → 应 403
- guest 访问 /api/files/shared:private/ → 应被拒
- 成员 A 访问 成员 B 的 private → 应 403
- 非 admin 传 X-As-User 头 → 应被忽略
- 创建指向他人 private 的分享 → 应被拒
- WebDAV 用登录密码访问（已设独立密码）→ 应失效
- 防爆破锁定期间用正确密码 → 应 429

**输出：** 每个向量一行：`场景 → 预期 → 实际代码行为 → 是否可利用`

### 对抗第 3 轮：竞态条件与并发攻击
**策略：分析所有共享状态的操作，寻找 TOCTOU 和竞态窗口。**

逐一分析：
- 两个请求同时上传同名文件 → 第二个是否进回收站（而非覆盖丢失）
- 同时删除和移动同一文件 → _db_lock 是否保护
- 配额检查（读当前用量）与实际写入之间 → 是否在锁内
- 秒传的 samestat 判断 → 是否有 TOCTOU（文件在 check 和 link 之间被替换）
- 会话验证（读 DB）与使用（处理请求）之间 → 会话是否可能在中间被吊销
- 防爆破计数器（读 fail_count）与写入之间 → 并发登录是否能绕过计数
- 分享下载计数（读 counted）与写入之间 → 并发下载是否重复计数

**输出：** 每个场景一行：`场景 → 竞态窗口位置 → 当前保护机制 → 残余风险`

### 对抗第 4 轮：信息泄露与 DoS 攻击
**策略：寻找所有可能泄露内部信息或耗尽资源的路径。**

**信息泄露：**
- .meta.db 通过 /preview 或 /download 可访问？
- .trash 目录内容可通过 API 列出？
- 错误响应包含堆栈跟踪或内部文件路径？
- audit_log 可被普通用户读取？
- 服务器版本信息通过 HTTP 头泄露？
- 分享页面泄露 owner 用户名？
- 设备列表泄露其他用户的设备信息？

**DoS/资源耗尽：**
- symlink loop → 是否有深度限制防止无限递归？
- 超大目录（10 万文件）→ 列表是否有分页或截断？
- 并发 100 个登录请求 → 防爆破是否有效？
- 超大 zip 下载 → 是否有文件数或大小限制？
- 超大分片上传 → MAX_CHUNKED_SIZE 是否生效？
- WebDAV PROPFIND 深度遍历 → 是否限制递归深度？

**输出：** 每个向量一行：`向量 → 代码位置 → 风险等级 → 当前防御`

### 对抗第 5 轮：边界条件与极端场景攻击
**策略：测试开发者最容易忽略的边界条件。**

**边界条件：**
- 空文件上传（0 字节）→ 是否正常处理？
- 空目录名创建 → 是否被拒绝？
- 超长文件名（255+ 字符）→ 是否截断或拒绝？
- Unicode 特殊字符文件名（RTL 覆盖、零宽字符）→ 是否正常显示？
- 路径末尾带 `/` vs 不带 → 行为是否一致？
- 同时对同一文件 share + delete → 最终状态是否一致？
- 分享过期瞬间的下载请求 → 是允许还是拒绝？
- Token 过期瞬间的续期请求 → 是否有边界处理？
- 数据库迁移过程中的并发请求 → 是否有锁保护？
- PG 和 SQLite 双引擎下行为差异 → 是否有引擎特定 bug？

**极端场景：**
- 所有磁盘空间用尽时的上传行为 → 是否优雅降级？
- PostgreSQL 宕机时的降级行为 → 是否回退到合理错误？
- Caddy 重启期间的请求 → API 是否仍然可用？
- 用户名包含特殊字符（空格、Unicode）→ 私人目录创建是否正常？

**输出：** 每个场景一行：`场景 → 预期行为 → 实际代码行为 → 风险`

## D. 严重度评估

对 B 轮（5 轮审查）和 C 轮（5 轮对抗）的所有发现统一评估：

- **P0 红线**：路径穿越可读 .meta.db、认证绕过、SQL 注入、任意文件删除/覆盖
- **P1 高危**：权限提升、信息泄露（内部路径/堆栈）、竞态数据损坏、Token 安全缺陷
- **P2 中危**：防爆破可绕过、filename sanitization 不完整、审计缺失、资源泄漏
- **P3 低危**：代码质量、文档不一致、性能优化空间
- **INFO**：已知取舍（提取码明文、Webhook 不限内网、WebDAV 仅密码等，记录即可）
